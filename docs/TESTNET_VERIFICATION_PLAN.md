## 1. 范围

验证分两段，第二段是否发生由另一次书面决定。

1. **只读核验。** 只允许第 2 节白名单中的主机、路径和 GET。记录账户模式、时钟、交易规则和钱包原文中的核验字段。
2. **限额试单。** 本方案不包含这次授权。只读核验全部通过之后，才可以单独决定是否允许一笔限额单。查询和撤单属于该次交易会话，不属于只读阶段。

撤单前已经成交或部分成交时如何记账、如何占用和是否还撤单，必须在那次试单授权里单独写明。本方案不提前规定，也不据此放行。

停止条件，满足任一条即终止当次验证，已发出的请求不再追加：

- 请求不在第 2 节白名单内，或出现跳转、非 HTTPS、关闭证书校验。
- 只读阶段出现 POST、PUT、PATCH、DELETE，或其他写方法，包括撤单。
- 日志或证据正文出现 API Key、签名值或完整签名 URL。
- 持仓模式、联合保证金、逐仓三项有任一缺失或不能按第 4.3 节核实。
- 第 4.1 节的三次时钟取样有任一未通过。
- 交易规则与本地名义额公式 `数量 × 价格`、合约单位 `1` 不一致。
- 只读阶段结束时，原订单库里仍有未解释的 UNKNOWN、QUERYING、CANCELING，或风险库里仍有该账户的阻断。

`HOLD` 在两段里都保持。将来若单独授权试单，发送仍只能走已绑定的模拟盘主机，并带上当次进程内的限额授权。改变实盘常量不属于本方案。

## 2. 只读白名单

只读运行器只能发出下表中的请求。主机固定为 `demo-fapi.binance.com`，方案为 `https`，端口为 `443`，方法为 `GET`。路径必须以单个 `/` 开始，URL 中不得带用户名或密码。

| 方法 | 路径 | 允许的查询 |
|---|---|---|
| GET | `/fapi/v1/time` | 无 |
| GET | `/fapi/v1/exchangeInfo` | 无 |
| GET | `/fapi/v1/positionSide/dual` | `recvWindow`、`timestamp`、`signature` |
| GET | `/fapi/v1/multiAssetsMargin` | `recvWindow`、`timestamp`、`signature` |
| GET | `/fapi/v2/positionRisk` | `symbol` 仅为 `BTCUSDT` 或 `ETHUSDT`，外加上述三项签名参数 |
| GET | `/fapi/v2/account` | `recvWindow`、`timestamp`、`signature` |
| GET | `/fapi/v1/openOrders` | `symbol` 仅为 `BTCUSDT` 或 `ETHUSDT`，外加上述三项签名参数 |

以下请求在发送前拒绝：

- 主机为 `fapi.binance.com`，或为上表以外的任何主机、端口或方案。
- 方法不是 GET。这包括 `POST /fapi/v1/order`、`DELETE /fapi/v1/order`，以及任何撤单路径。
- 路径不在上表中，或 `symbol` 不是 `BTCUSDT` 与 `ETHUSDT` 之一。
- HTTP 3xx。运行器不读取跳转目标，不跟随新地址。
- 关闭证书校验。TLS 使用系统证书库；证书库缺失时使用 `/etc/ssl/cert.pem`。

签名材料放在查询串的 HMAC-SHA256 中。密钥本身不得出现在查询串。请求头只带 `X-MBX-APIKEY`。日志、证据正文和异常文本同时去掉三段内容：API Key、`signature` 的值、带查询串的完整 URL。可以保留方法、路径、主机和 HTTP 状态。

## 3. 账户、凭据和网络隔离

使用一个专用的币安 USD-M 模拟盘账户。该账户的密钥不用于 `https://fapi.binance.com`。

凭据只来自本机环境变量 `CTS_BINANCE_API_KEY` 和 `CTS_BINANCE_API_SECRET`。`.env` 已被仓库忽略。证据只记录“凭据已在本机环境变量中，未写入仓库”，以及 `CTS_BINANCE_NETWORK=TESTNET`。不记录密钥、密钥长度、密钥哈希或签名。

只读阶段要求：

- `CTS_BINANCE_NETWORK` 必须是 `TESTNET`。缺失或为其他值时，不读取钱包。
- 传输工厂只能绑定 `TESTNET_BASE = https://demo-fapi.binance.com`。绑定到主网主机时，请求在发送前失败。
- 本地账户编号、订单库路径、风险库路径在当次证据里互相绑定。重启必须打开原来的两个库文件。路径缺失时不新建空库，也不开新仓。
- 进程授权语句必须等于：`授权本进程在限额内向币安发送 BTC/ETH USDT 逐仓单向实盘单`。品种只含 `BTCUSDT` 与 `ETHUSDT`。`max_notional` 大于 0，`expires_at` 晚于当次 UTC 时间。这些字段出现在试单授权里；只读阶段不使用它们发单。

只读阶段使用的密钥只需能够完成第 2 节的签名 GET。试单若被另一次决定授权，再使用允许交易的密钥，并只在该次交易会话中开放写请求。两段密钥都不进入仓库。只读运行器即使持有可交易密钥，也没有第 2 节以外的发送能力。

## 4. 只读接口、时间同步及交易规则

所有时间写成 UTC。签名请求的 `recvWindow` 为 `5000`，`timestamp` 使用当次真实 UTC 毫秒，不使用测试夹具里的固定时间。

当前产品源码尚未请求服务器时间，也尚未请求交易规则。这两项是本方案的只读核验步骤，不是 S1-B 的遗留改动。核验运行器在方案冻结后再单独实现；实现前不发请求。

### 4.1 时钟

公开 `GET /fapi/v1/time` 取样三次。三次各自重新发起请求，不复用同一次响应。每次记录三个毫秒整数：

- `t0`：发送前的本地 UTC。
- `t1`：收完响应正文后的本地 UTC。
- `serverTime`：该次正文中的服务器时间。

该次往返延迟 `RTT = t1 - t0`。测量不确定度 `u = RTT / 2`。偏移估计 `offset = serverTime - (t0 + t1) / 2`。单次通过条件是 `|offset| + u ≤ 1000` 毫秒。`u > 1000` 时，偏移无法从往返延迟中分开，该次未通过。

三次全部通过，时钟验收才通过。任一次未通过，则整项未通过，后续签名请求都不发送。不把单次 `serverTime` 与本地时间的直接差当作验收依据。

### 4.2 交易规则

公开 `GET /fapi/v1/exchangeInfo`。对 `BTCUSDT` 和 `ETHUSDT` 分别保留用于判断的规则原文，并记录这段原文的 SHA256。判断字段包括：合约状态、合约类型、报价资产、保证金币种、价格最小变动、数量步长、最小数量，以及最小名义额字段的原名和原值。

通过标准：

- 两个品种都可交易，且为 USDT 本位永续。
- 本地名义额按 `数量 × 价格` 计算，合约单位为 `1`。规则若要求另一套面值，本项失败。
- 证据保留规则原文及其 SHA256。方案不预写步长和最小名义额。

### 4.3 账户模式

下列请求均为第 2 节中的签名 GET，`recvWindow=5000`。原因码沿用 `ACCOUNT_MODE_DRIFT`。

| 路径 | 通过标准 |
|---|---|
| `GET /fapi/v1/positionSide/dual` | `dualSidePosition` 明确为 `false` |
| `GET /fapi/v1/multiAssetsMargin` | `multiAssetsMargin` 明确为 `false` |
| `GET /fapi/v2/positionRisk?symbol=BTCUSDT` | 对应行的 `marginType` 不区分大小写等于 `isolated` |
| `GET /fapi/v2/positionRisk?symbol=ETHUSDT` | 同上 |

字符串 `"false"` 与布尔值 `false` 可以接受。字段缺失、正文无法解析、没有对应品种行，或 `marginType` 无法核实为逐仓，结论都是未通过。这些情况不写成 `NOT_RUN`，也不写成通过。

### 4.4 钱包与未完成委托

签名 `GET /fapi/v2/account`。只提取 USDT 的 `walletBalance`、`availableBalance`、`unrealizedProfit`、`marginBalance`。没有 USDT 行则未通过。数字以返回原文记录，不改写、不补零、不用本地账本覆盖。

签名 `GET /fapi/v1/openOrders` 分别查询两个品种。记录返回的委托笔数和 `clientOrderId`。存在本系统未登记的委托时，只读核验记为未通过，试单讨论不开始。

钱包读取失败时，界面与证据保持“币安模拟盘读取失败”和“暂无证据”，不回填上一次成功读数。

## 5. 单笔限额、查询撤单与异常退出

本节描述将来单独授权时必须满足的形状。它本身不是授权，也不给只读阶段增加写权限。

### 5.1 单笔限额

一次授权只允许一笔新订单，品种是 `BTCUSDT` 或 `ETHUSDT` 之一。订单类型是 `LIMIT`，`timeInForce` 是 `GTC`，`reduceOnly` 是 `false`。减仓写单保持拒绝。

授权书要写明：授权人、本地账户编号、品种、方向、数量、价格、`max_notional`、`client_order_id`、到期时间，以及撤单前已成交和部分成交的处置。数量和价格必须符合第 4.2 节当时读到的步长。名义额等于 `数量 × 价格`，大于 0，且不超过当次 `max_notional`。价格放在不预期立即成交的一侧。若发送前或撤单前已经全部成交或部分成交，按该次授权书写明的处置执行；授权书没有写明时，不发送这张单。

发送前重新读取第 4.3 节的三项账户模式。发送锁覆盖“复查、占住派发、POST”这一段。同一 `client_order_id` 只允许一次 POST。意图先写入原订单库，再发送。

### 5.2 查询和撤单

查询和撤单只存在于后续另行授权的交易会话。只读阶段不查询单笔订单，也不撤单。

交易会话中，POST 返回后先查询，再按授权书决定是否撤单。查询和撤单都要核对 `clientOrderId`、`symbol`、`side`、`origQty`。身份缺失或冲突时，订单记为 UNKNOWN，额度继续占用，不把这次响应当成终态。

授权书写明“未成交才撤单”时，顺序是：

1. 查询确认状态。未成交时，状态为 `NEW`，`executedQty` 为 0。
2. 发送一次撤单。
3. 再查询。终态为 `CANCELED` 时，这笔订单释放未成交占用。
4. 若查询或撤单超时，订单记为 UNKNOWN 并保留阻断。同一订单库上的后续查询在身份和数量都核对通过后，只解除已经结束的那次请求。

查询结果已经是全部成交或部分成交时，本方案不给出默认动作。没有对应授权条款，就不撤单，也不释放未知占用。

同一账户上另一笔仍在传输层的请求保持阻断。新预留在阻断还在时失败，原因码 `UNKNOWN_ORDER`。

### 5.3 异常退出

只读阶段的进程退出不发送撤单，也不补发任何写请求。只读运行器没有撤单权限。

“退出后必要时撤单”只适用于后续另行授权的交易会话。该会话的恢复只做三件事：打开原来的订单库和风险库、查询、按该次授权书撤单。不补发，不新建数据库。授权书没有写明撤单前成交处置时，恢复后只查询，不撤单。

已有本地验收覆盖这些中断，真实网络阶段不主动制造进程死亡：

- 恢复证据已经写入、旧阻断尚未删除。
- 请求结束标记、对账确认、阻断清理之间再次中断。
- 锁路径缺失、锁文件被替换，或打开后的文件描述符与登记的设备号和 inode 不一致。

死亡证据只有一种：重新打开的描述符与登记身份一致，并且同一个描述符能够被独占。否则阻断保持，不写 `recovered_at`。

真实交易会话上的非计划退出，恢复后先查询交易所。查询确认终态之前，不释放未知占用，也不开新单。

## 6. 证据合同

每次只读核验产生一份证据目录。目录可以留在本机，不把含有账户原文的包提交进仓库。日志与证据正文使用同一套脱敏：去掉 API Key、`signature` 的值和完整签名 URL。

| 编号 | 内容 |
|---|---|
| E1 | 被核验源码的完整 Git SHA，以及本方案当时的提交 SHA |
| E2 | 采集开始与结束的 UTC 时间。每条请求另记采集时刻 |
| E3 | 账户绑定：本地账户编号、订单库路径、风险库路径、`CTS_BINANCE_NETWORK`、实际主机 |
| E4 | 每条请求的方法、路径、主机、HTTP 状态。不含查询串、API Key、签名和完整签名 URL |
| E5 | 第 4 节每个检查的期望、观察到的字段原文、结论。结论只使用 `PASS`、`FAIL`、`NOT_RUN` |
| E6 | 三次时钟取样的 `t0`、`t1`、`serverTime`、`RTT`、`u`、`offset`，以及每项是否满足 `\|offset\| + u ≤ 1000` |
| E7 | 两个品种的规则原文，以及这段原文的 SHA256 |
| E8 | USDT 钱包四个字段的原文；失败时写“暂无证据” |
| E9 | 未完成委托笔数与 `clientOrderId` |
| E10 | 凭据声明：已在本机环境变量中，未写入仓库。网络变量为 `TESTNET` |
| E11 | 证据目录自身的 SHA256 |

模式字段缺失，或无法核实逐仓时，E5 中该项为 `FAIL`。必查项不得以 `NOT_RUN` 代替缺失证据。

总结论只有在 E5 的必查项全部为 `PASS`，且 E6、E7 齐全时写成“只读核验通过”。其中任一项为 `FAIL` 或 `NOT_RUN`，总结论为“只读核验未通过”。两种结论都不等于试单授权，也不等于实盘放行。

试单若以后被授权，另外增加：授权书原文、其中关于已成交和部分成交的条款、唯一 POST 的时间、查询与撤单的身份字段和状态、订单库与风险库路径、结束时的阻断笔数。中途退出时还要记录重启后的第一次查询结果，以及是否按授权书执行了撤单。

## 7. 冻结与下一步

本文件仍是草案。明确接受全文之后才标记为冻结，并记下冻结时的源码 SHA。冻结前可以修改方案，不实现运行器，不访问币安。

冻结后的顺序：

1. 单独实现只读核验运行器。它只能发送第 2 节白名单中的 GET，不能撤单。
2. 在另一次决定之后，才执行只读核验。
3. 只读证据按第 6 节关闭后，再单独决定是否授权一笔限额试单。该决定必须写明撤单前已成交和部分成交的处置。
4. S1-B 不再扩展。`main` 不合并。实盘常量保持 `HOLD`。
